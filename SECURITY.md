# Security Policy

## Supported scope

Security reports are accepted for the current default branch, active workflows, dependency configuration, deterministic validators, reference implementations, and retained evidence-processing code in this repository.

Scientific disagreement, an unproved mathematical claim, a failed benchmark, or evidence that a research result does not generalize is not by itself a software-security vulnerability. Report those matters through the governed issue and review process unless they also expose a concrete confidentiality, integrity, availability, authentication, authorization, supply-chain, or code-execution risk.

## Reporting a vulnerability

Do not open a public issue for an unpatched vulnerability.

Use GitHub private vulnerability reporting from the repository Security tab when that facility is available. Until it is enabled, contact the Grand Challenge organization owner through an established private channel.

Include:

- the affected file, workflow, dependency, interface, or commit;
- the security impact and plausible threat model;
- reproducible steps or a minimal proof of concept;
- known preconditions and affected versions;
- a suggested mitigation, when available.

Do not include credentials, private keys, access tokens, personal data, or unrelated confidential material.

## Response and disclosure

The project will aim to acknowledge a complete report within five business days. Triage will determine severity, affected scope, containment, remediation, validation, and disclosure timing.

Public disclosure should occur only after a validated correction or an explicitly coordinated disclosure decision. Repository governance records may retain bounded evidence of the response without publishing exploit details before remediation.

## Claim boundary

Acceptance, triage, or correction of a security report does not certify mathematics, establish quantum advantage, validate hardware, demonstrate deployment safety, or authorize manufacturing, product, or commercial claims.
